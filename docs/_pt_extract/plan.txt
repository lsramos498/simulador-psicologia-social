1.  Introducción
El presente documento tiene como finalidad establecer el plan de pruebas para el proyecto Lumina, Simulador de Psicología Social, una aplicación desarrollada para apoyar el aprendizaje mediante la presentación de situaciones sociales en las que los estudiantes deben analizar escenarios, tomar decisiones y reflexionar sobre sus respuestas.
El plan de pruebas busca verificar el correcto funcionamiento de los diferentes módulos del sistema, incluyendo la gestión de usuarios, roles y permisos, la creación de casos y escenarios, la administración de sesiones y el registro de respuestas de los estudiantes.
Para ello, se definirán casos de prueba que permitan evaluar tanto situaciones correctas como condiciones incorrectas o inesperadas, con el propósito de identificar posibles errores y comprobar que las funcionalidades cumplan con los requisitos establecidos.
De esta manera, se pretende contribuir a la calidad, confiabilidad y seguridad del software durante su proceso de desarrollo, facilitando la detección oportuna de fallos y la mejora continua del sistema.
2.  Alcance
El presente plan de pruebas comprende la evaluación de las principales funcionalidades del proyecto Lumina, Simulador de Psicología Social, con el propósito de verificar que los diferentes módulos del sistema cumplan con los requisitos establecidos y funcionen correctamente.
Las pruebas estarán enfocadas en la gestión de usuarios, roles y permisos, la creación y administración de casos y escenarios de simulación, el control de las sesiones, el registro y consulta de respuestas de los estudiantes, el seguimiento de su progreso y la generación de notificaciones relacionadas con su participación.
Se realizarán pruebas funcionales que permitan comprobar el comportamiento del sistema ante situaciones correctas e incorrectas, incluyendo la validación de datos, el control de acceso, las restricciones según el estado de las sesiones y el almacenamiento adecuado de la información en la base de datos.
El alcance también contempla la verificación de la integración entre los módulos del sistema, a medida que estos sean desarrollados, para identificar posibles errores en la comunicación entre sus componentes.
Dado que Lumina se encuentra en proceso de desarrollo, las pruebas se planificarán para las funcionalidades previstas y se ejecutarán progresivamente sobre aquellas que estén implementadas y disponibles. Las funcionalidades pendientes de desarrollo o integración se documentarán como pruebas no ejecutadas hasta que puedan ser verificadas.
De esta manera, el plan permitirá realizar un seguimiento de la calidad del software, identificar fallos y comprobar el cumplimiento de los requisitos durante las diferentes etapas del proyecto.
3. Definiciones, siglas y abreviaturas
A continuación, se presentan los principales conceptos, términos y abreviaturas utilizados en el presente plan de pruebas, con el propósito de facilitar su comprensión.
Plan de pruebas: Documento que establece las actividades, objetivos, estrategias y recursos necesarios para verificar el funcionamiento y la calidad de un sistema de software.
Caso de prueba: Conjunto de condiciones, datos de entrada y pasos que permiten comprobar si una funcionalidad del sistema produce los resultados esperados.
Pruebas funcionales: Pruebas que verifican que las funciones del software se comporten de acuerdo con los requisitos establecidos.
Pruebas unitarias: Pruebas realizadas sobre funciones o componentes individuales del software para comprobar que funcionan correctamente de manera independiente.
Pruebas de integración: Pruebas que permiten verificar la interacción entre diferentes componentes del sistema, como la comunicación entre el Backend y la base de datos.
Escenario positivo: Situación de prueba en la que se utilizan datos válidos y se espera que el sistema realice correctamente la operación solicitada.
Escenario negativo: Situación de prueba en la que se utilizan datos incorrectos o condiciones no permitidas para verificar que el sistema controle adecuadamente los errores.
Criterio de aceptación: Condición que debe cumplirse para considerar que una funcionalidad o caso de prueba funciona correctamente.
Backend: Parte del software encargada de procesar las solicitudes, aplicar las reglas del sistema y gestionar la información almacenada en la base de datos.
Frontend: Parte visual de la aplicación mediante la cual los usuarios interactúan con las funcionalidades del sistema.
Base de datos: Sistema organizado de almacenamiento que permite guardar, consultar y administrar la información de Lumina, como usuarios, sesiones y respuestas.
MySQL: Sistema de gestión de bases de datos relacionales utilizado en el proyecto para almacenar la información.
API REST: Interfaz que permite la comunicación entre diferentes componentes del software mediante solicitudes HTTP.
Patrón de diseño: Solución reutilizable para organizar el código y resolver problemas frecuentes durante el desarrollo de software.
Observer (Observador): Patrón de diseño que permite notificar automáticamente a los componentes suscritos cuando ocurre un evento determinado.
State (Estado): Patrón de diseño que permite modificar el comportamiento de un objeto según su estado, como una sesión sin iniciar, en curso o finalizada.
Proxy: Patrón de diseño que permite controlar el acceso a determinadas funcionalidades mediante un componente intermediario.
Sesión de simulación: Participación de un estudiante en una actividad de Lumina, durante la cual puede analizar situaciones y registrar sus decisiones.
Validación de datos: Proceso mediante el cual se comprueba que la información ingresada cumple con las condiciones establecidas por el sistema.
Resultado esperado: Comportamiento que debería presentar el software al ejecutar un caso de prueba.
Resultado obtenido: Comportamiento real observado después de ejecutar una prueba, que se compara con el resultado esperado.
Git: Herramienta de control de versiones que permite registrar y administrar los cambios realizados en el código fuente.
GitHub: Plataforma utilizada para almacenar el repositorio del proyecto y facilitar la colaboración entre las integrantes del equipo.

5. Plan De Pruebas
El Plan de Pruebas del proyecto Lumina, Simulador de Psicología Social tiene como objetivo verificar el correcto funcionamiento de los módulos que conforman el sistema, mediante la ejecución de pruebas que permitan comprobar el cumplimiento de los requisitos funcionales establecidos.
Se realizarán pruebas con datos válidos e inválidos para evaluar el comportamiento de las funcionalidades, identificar posibles errores y garantizar que el sistema responda adecuadamente ante diferentes situaciones.
Las pruebas se desarrollarán progresivamente, de acuerdo con el estado de implementación de cada módulo.
5.1. Módulo de gestión de sesiones y actividades
Responsable: Laura Sofía Ramos Reyes.
Descripción del módulo:
Este módulo permite administrar las actividades de simulación y controlar el ciclo de vida de las sesiones de los estudiantes, teniendo en cuenta los estados Sin iniciar, En curso y Finalizado.
Objetivo de las pruebas:
Verificar que las sesiones se creen y administren correctamente, que los cambios de estado cumplan con las reglas establecidas y que el sistema impida operaciones no permitidas.
5.1.1. Casos de prueba planeados para el módulo
CP-01: Verificar la creación y programación de una actividad de simulación.
CP-02: Verificar el inicio correcto de una sesión.
CP-03: Comprobar que una sesión pueda pasar del estado En curso a Finalizado.
CP-04: Verificar que el sistema rechace transiciones de estado no permitidas.
CP-05: Comprobar el comportamiento del sistema cuando se intenta acceder a una actividad fuera de las condiciones establecidas.
CP-26: Verificar la notificación de convocatoria y de cambios de estudiantes.
CP-27: Verificar el control del tiempo máximo de participación.
CP-28: Verificar la restricción de ingreso tardío.
CP-32: Verificar la autorización de repetición excepcional.
5.2. Módulo de autenticación, roles y permisos
Responsable: Sofía Gallego Bedoya.
Descripción del módulo:
Este módulo se encarga de gestionar la identificación de los usuarios, controlar sus permisos de acceso y validar los códigos de autorización para participar en las actividades de simulación.
Objetivo de las pruebas:
Comprobar que el sistema permita el acceso a los usuarios autorizados y restrinja las operaciones que no correspondan a sus permisos.
5.2.1. Casos de prueba planeados para el módulo
CP-06: Verificar el acceso de un usuario con credenciales válidas.
CP-07: Comprobar el rechazo de credenciales incorrectas.
CP-08: Verificar que los usuarios solamente puedan acceder a las funcionalidades autorizadas.
CP-09: Comprobar que un código de autorización válido permita el acceso correspondiente.
CP-10: Verificar el rechazo de códigos inválidos o no autorizados.
5.3. Módulo de gestión de casos, escenas y decisiones
Responsable: Stefanía Díaz Raigoza.
Descripción del módulo:
Este módulo permite administrar los casos de psicología social que se presentan a los estudiantes, incluyendo sus escenas, preguntas y opciones de decisión.
Objetivo de las pruebas:
Verificar que los casos y sus elementos se registren correctamente, que la información cumpla con las validaciones establecidas y que se mantengan las relaciones correspondientes entre casos, escenas y decisiones.
5.3.1. Casos de prueba planeados para el módulo
CP-11: Verificar la creación de un caso con información válida.
CP-12: Comprobar el rechazo de un caso con información obligatoria incompleta.
CP-13: Verificar la creación de escenas asociadas a un caso.
CP-14: Comprobar el registro de decisiones y opciones asociadas a una escena.
CP-15: Verificar que el sistema rechace relaciones incorrectas entre casos, escenas y decisiones.
CP-25: Verificar el registro de la rúbrica, la publicación y el archivo del caso.
5.4. Módulo de participación y respuestas
Responsable: Valeria Tobar Garzón.
Descripción del módulo:
Este módulo permite registrar y consultar las respuestas seleccionadas por los estudiantes durante las simulaciones de psicología social. También contempla las validaciones necesarias para controlar la participación, evitar registros duplicados y gestionar el seguimiento del progreso del estudiante.
Objetivo de las pruebas:
Comprobar que las respuestas se registren correctamente en la base de datos, que correspondan al estudiante y a la sesión autorizada y que el sistema rechace operaciones inválidas. 5.4.1. Casos de prueba planeados para el módulo
CP-16: Verificar el registro correcto de una respuesta válida.
CP-17: Comprobar que las respuestas registradas se almacenen y consulten correctamente en MySQL.
CP-18: Verificar que un estudiante no pueda consultar respuestas pertenecientes a otro estudiante.
CP-19: Comprobar que no se puedan registrar respuestas cuando la sesión esté finalizada.
CP-20: Verificar el rechazo de opciones que no correspondan a la decisión seleccionada.
CP-21: Comprobar que no se registren respuestas duplicadas para una misma decisión y sesión.
CP-22: Verificar que una respuesta pueda modificarse únicamente cuando las condiciones de la sesión lo permitan.
CP-23: Comprobar el cálculo del progreso del estudiante durante la simulación.
CP-24: Verificar el funcionamiento del patrón Observer ante eventos relacionados con la participación.

5.6. Estrategia y niveles de prueba
El plan cubre todos los requisitos funcionales del proyecto (RF-01 a RF-27), con al menos un escenario positivo y uno negativo por funcionalidad. Los casos CP-01 a CP-26 se ejecutaron; los casos CP-27 a CP-36 corresponden a funcionalidades que aún no están implementadas y quedan planificados.
Las pruebas se ejecutaron el 03/11/2026 sobre la versión integrada del código (rama develop, idéntica a la rama integracion). Se combinaron tres niveles:
Pruebas unitarias automatizadas del repositorio con node:test: 303 pruebas, 301 aprobadas y 2 omitidas por diseño (las que requieren MySQL real, que se ejecutaron aparte).
Pruebas de integración con MySQL real: acceso.mysql.test.js (5 de 5 aprobadas) y participacion.mysql.test.js (4 de 5 subpruebas aprobadas; ver D-03).
Pruebas funcionales de caja negra sobre la API REST: el servidor real (src/server.js) se levantó contra una base creada con el esquema oficial y se enviaron solicitudes con escenarios positivos y negativos. Cada resultado se comprobó con consultas SQL.
Técnicas aplicadas: partición de equivalencia (datos válidos e inválidos), valores límite (fechas, tiempos, identificadores), pruebas de transición de estados (patrón State), pruebas de control de acceso (Proxy y middlewares) y verificación de integridad en la base de datos.
5.7. Entorno de pruebas
Código: rama develop del repositorio simulador-psicologia-social, backend v1.0.0 (corte del 02/11/2026).
Ejecución: Node.js 22, Express 5, mysql2 y jsonwebtoken, según backend/package.json.
Base de datos: esquema backend/database/schema.sql (27 tablas) cargado en MariaDB 10.11, compatible con MySQL. Se recomienda repetir las pruebas de integración en MySQL 8.0.16 o superior antes de la entrega final.
Datos iniciales: seed del módulo de acceso (npm run db:seed): roles Administrador, Docente y Estudiante, permiso CREAR_CASOS y administrador inicial.
Herramientas: node --test (pruebas automatizadas), un script de solicitudes HTTP para la API y consultas SQL de verificación. Las capturas de cada caso se tomaron de esa ejecución.

5.9. Criterios de aceptación y suspensión
Aprobado: todos los escenarios del caso coinciden con la respuesta esperada.
Aprobado con observaciones: el comportamiento esperado se cumple, pero hay una limitación que impide probar el flujo completo (funcionalidad sin endpoint, datos preparados por SQL o prueba automatizada desactualizada).
No aprobado: al menos un escenario no coincide con la respuesta esperada. Se registra un defecto.
No ejecutado: la funcionalidad aún no está implementada; el caso queda definido y se ejecutará cuando se integre.
Suspensión: las pruebas se suspenden si el servidor o la base de datos no están disponibles, o si el esquema no corresponde al del repositorio.
